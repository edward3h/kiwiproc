<1> Use the `call` or `run` methods, which are passed an instance of "dao" in a transaction.

If the callback completes normally the transaction is committed.
If the callback throws a `SQLException` (or an `UncheckedSQLException` from a nested DAO call), the transaction is rolled back and the exception is re-thrown wrapped in an `UncheckedSQLException`.

[[auto-commit]]
=== Single-statement calls and auto-commit

By default, calling a DAO method directly on the generated provider (outside `call`/`run`) runs that one method in its own transaction: `setAutoCommit(false)`, the statement, `commit()`, `setAutoCommit(true)`.
For a lone statement this is unnecessary, because a single statement is already atomic under auto-commit.

Set `autoCommit = true` on `@DAO` to run `@SqlQuery` and `@SqlUpdate` methods called directly on the provider on a connection in auto-commit mode, with no `BEGIN`/`COMMIT` round trips:

[source,java]
----
@DAO(autoCommit = true)
public interface TagDao {
    @SqlQuery("SELECT name FROM tags")
    List<String> allNames();
}
----

This does not affect explicit `call`/`run` blocks, `@SqlBatch` methods, or methods returning `Stream`; these stay transactional.
It does change statements that rely on the enclosing transaction: for example, the row locks taken by `SELECT ... FOR UPDATE` are released as soon as the statement completes.
The default is `false`.

The setting can be overridden per method with the `autoCommit` attribute of `@SqlQuery` and `@SqlUpdate`, which takes an `AutoCommitMode`: `INHERIT` (the default, use the `@DAO` setting), `ENABLED` or `DISABLED`.
Use `DISABLED` for a statement that needs a transaction on an otherwise auto-commit DAO:

[source,java]
----
@DAO(autoCommit = true)
public interface TagDao {
    @SqlQuery("SELECT name FROM tags")
    List<String> allNames(); // auto-commit

    @SqlQuery(sql = "SELECT id FROM tags WHERE name = :name FOR UPDATE", autoCommit = AutoCommitMode.DISABLED)
    long lockByName(String name); // own transaction
}
----

[[streaming]]
=== Streaming

A `@SqlQuery` method may return `java.util.stream.Stream<T>` to stream rows lazily from the database rather than buffering them into a `List`.

[source,java]
----
@SqlQuery("SELECT id, name FROM types ORDER BY id")
Stream<PetType> streamPetTypes();
----

Unlike `List`-returning methods, stream-returning methods are **not** wrapped in a `call()` transaction.
Each streaming method acquires its own JDBC connection with `autoCommit=false` (required for PostgreSQL server-side cursors).

**The caller is responsible for closing the stream**, which commits the transaction and closes the connection.
Use try-with-resources:

[source,java]
----
try (var stream = petClinicDAOProvider.streamPetTypes()) {
    stream.forEach(pet -> process(pet));
}
----

Use `@SqlQuery(fetchSize = N)` to enable PostgreSQL server-side cursoring (fetching rows in batches rather than all at once):

[source,java]
----
@SqlQuery(value = "SELECT id, name FROM types ORDER BY id", fetchSize = 100)
Stream<PetType> streamPetTypes();
----

[WARNING]
====
Failing to close the stream will leak the database connection.
Always use try-with-resources or call `stream.close()` explicitly.
====
